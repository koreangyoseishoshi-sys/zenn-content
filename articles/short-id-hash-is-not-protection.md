「個人情報はハッシュ化して保存しているので安全です」。

この説明は、**値の種類が少ないデータには通用しません**。6桁の患者番号や職員番号、生年月日は、全部の候補をハッシュにして見比べれば元に戻せるからです。

この記事では、桁の少ない個人情報を「照合はできるが、漏れても読めない」形で持つための設計をまとめます。題材は、私が社内向けに作っている業務システム（スプレッドシート＋Google Apps Script と、Windowsの常駐ツール）です。

## 6桁の番号は、全部試すのに0.4秒

試してみます。6桁の番号 `804721` を SHA-256 にした値だけが漏れたとします。

```js
const crypto = require('crypto');
const target = crypto.createHash('sha256').update('804721').digest('hex');

console.time('6桁を全部試す');
for (let i = 0; i < 1_000_000; i++) {
  const s = String(i).padStart(6, '0');
  if (crypto.createHash('sha256').update(s).digest('hex') === target) {
    console.log('見つかった:', s);
    break;
  }
}
console.timeEnd('6桁を全部試す');
```

```
見つかった: 804721
6桁を全部試す: 397.13ms
```

手元のノートPC（Apple M1）で **0.4秒** でした。特別な道具は何も使っていません。

SHA-256 が弱いのではありません。**候補が100万通りしかない**ことが問題です。生年月日なら、100年分でも約3万6500通りしかありません。

| データ | 候補の数 | 全部試す時間の目安 |
|---|---|---|
| 6桁の番号 | 100万 | 1秒未満 |
| 生年月日（100年分） | 約3万6500 | 一瞬 |
| 電話番号（携帯） | 数億 | 数分〜 |

「ソルト（ランダムな値）を足せば？」と思うかもしれません。ソルトが**ハッシュと同じ場所に保存されている**なら、相手はソルトを足して同じように100万回試すだけです。1件あたりの手間は変わりません。

## 対策1：照合に使う値は「鍵付き」にする（HMAC）

照合（「この番号の人はリストに載っているか」）に必要なのは、**同じ番号から必ず同じ値が出る**ことです。これは残したまま、**鍵を知らない人には計算できない**ようにします。それが HMAC（鍵付きハッシュ）です。

```js
// Google Apps Script の例
function matchKey_(rawNo) {
  // 表記ゆれをそろえてから変換する（例：先頭の0を外す）
  const normalized = String(rawNo).trim().replace(/^0+(?=\d)/, '');
  const secret = PropertiesService.getScriptProperties().getProperty('MATCH_SECRET');
  const bytes = Utilities.computeHmacSha256Signature(normalized, secret);
  return Utilities.base64EncodeWebSafe(bytes);
}
```

鍵（`MATCH_SECRET`）は**データと別の場所**に置きます。データ（シート）だけが漏れても、鍵がなければ100万通りを試すことができません。

### 落とし穴：変換する前に「表記」をそろえる

実際にやって困ったのがここです。同じ患者番号でも、

- 手入力では6桁
- バーコードの中身は7桁で、先頭に `0` が付く
- 紙に印字された番号は `0` なし

と、**場所によって表記がそろっていません**でした。ハッシュは1文字違えばまったく別の値になります。表記をそろえずに変換すると、本人なのに一致しません。

**照合の決まりを作る前に、現物（バーコードの中身・印字・入力画面）を見比べる。** そろえ方を決めてから変換します。

## 対策2：画面に出す値は「毎回ちがう暗号文」にする

HMAC は元に戻せません。画面に名前や番号を表示したいなら、元に戻せる暗号化が別に必要です。

ここで、照合用と同じ「同じ値なら同じ結果」の方式を使ってはいけません。暗号文が同じなら**同じ人だと分かってしまう**からです。表示用は、毎回ランダムな値（IV）を混ぜて、**同じ名前でも毎回ちがう暗号文**になる方式（AES-GCM など）にします。

```js
// ブラウザの標準機能（Web Crypto API）の例
async function encryptForDisplay(dataKey, text) {
  const iv = crypto.getRandomValues(new Uint8Array(12)); // 毎回ちがう値
  const ct = await crypto.subtle.encrypt(
    { name: 'AES-GCM', iv }, dataKey, new TextEncoder().encode(text)
  );
  return { iv, ct }; // iv は秘密ではない。暗号文と一緒に保存してよい
}
```

つまり、1つの項目に**役割の違う2つの値**を持たせます。

| 用途 | 方式 | 性質 |
|---|---|---|
| 照合用 | HMAC（鍵付きハッシュ） | 同じ入力→同じ値。元に戻せない |
| 表示用 | AES-GCM など | 同じ入力でも毎回ちがう値。鍵があれば戻せる |

### 見本：同じ番号を3つの方式にかけると

番号 `804721` を、それぞれの方式に2回ずつかけた実際の出力です（鍵は説明用の仮のもの。長い値は途中で切っています）。

| 方式 | 1回目 | 2回目 | 読み取れること |
|---|---|---|---|
| SHA-256（鍵なし） | `d491867edc02…` | `d491867edc02…` | 毎回同じ。**誰でも同じ計算ができる** → 全部試せば戻る |
| HMAC（鍵A） | `YTlhRdb7T664…` | `YTlhRdb7T664…` | 毎回同じ → 照合に使える。鍵Aがないと計算できない |
| HMAC（鍵B） | `g0V_2F0ppzF3…` | — | 鍵が違えば、同じ番号でもまったく別の値 |
| AES-GCM | `iIAHqcmW…ezwG6r…` | `ZNxyOHbM…4AQM2s…` | **毎回ちがう** → 同じ人かどうかも分からない。鍵があれば戻せる |

ついでに、1つ隣の番号 `804722` の SHA-256 は `65113e69508a…` です。**1文字違うだけで、似ても似つかない値**になります。前の節の「表記をそろえてから変換する」が大事なのは、このためです。

## 対策3：生年月日で本人確認するなら「遅く」して「秘密を混ぜる」

本人に自分の申請内容を見せたい場面がありました。ログインの仕組みはなく、本人だけが知っているのは生年月日くらいです。

生年月日から鍵を作ると、候補は3万6500通りしかありません。そこで2つ足します。

1. **計算をわざと遅くする**：PBKDF2 のような、繰り返し回数を指定できる方式を使います。60万回繰り返すと、1回の計算に約72ms（M1で実測）かかります。3万6500通りを全部試すと **約44分** です
2. **サーバーだけが持つ秘密の値を混ぜる**：シートだけを手に入れた相手は、そもそも計算を始められません

この方式なら、照会のときは「その生年月日で名前を戻せたか」で本人確認ができます。**生年月日そのものを保存する必要がなくなります。**

## 鍵をどこに置くか

ここまでの対策は、**鍵とデータが別の場所にある**ことが前提です。私の構成では、名前を戻すための材料を3か所に分けています。

| 材料 | 置き場所 |
|---|---|
| 暗号文・照合用の値 | スプレッドシート |
| 鍵の部品・秘密の値 | スクリプトの設定（シートとは別） |
| 管理者パスワード・生年月日 | 人の頭の中（どこにも保存しない） |

シートをコピーされても、誤って共有しても、外部のツール（AIの接続など）がシートを読んでも、見えるのは読めない文字列だけです。

## この設計で守れないもの

正直に書いておきます。

- **シートと「秘密の値」が両方漏れたら**、生年月日の総当たりは成立します。遅くしてあるので1人あたり約44分かかりますが、**時間を稼いでいるだけで、防げてはいません**。この設計が強いのは「どちらか片方が漏れた場合」です
- 画面に表示した時点で、その画面を見ている人には読めます。暗号化は**保存場所の守り**であって、画面の守りではありません
- 暗号の部品は**自作していません**。HMAC・AES-GCM・PBKDF2 は、GAS とブラウザの標準機能だけで作っています。自作の暗号ほど危ないものはありません

## まとめ

- 桁の少ない個人情報は、**ハッシュにしても全部試せば戻せる**（6桁で0.4秒）
- 照合用は **HMAC**、表示用は**毎回ちがう暗号文**。1つの項目に2つの値を持たせる
- 生年月日のような弱い秘密から鍵を作るなら、**遅くする＋サーバーの秘密を混ぜる**
- いちばん効くのは暗号の強さより、**鍵をどこに・誰に持たせるか**
- 守れない範囲（両方漏れた場合）も書いておく

パスワードからデータ鍵を作らず、「データ鍵を包む」形にしている理由は、別の記事で書く予定です。
